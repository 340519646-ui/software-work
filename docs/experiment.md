## 一、实验目标与口径

对应 README 的 G1–G5，本阶段能验证的部分是「**抽取链路是否成立、是否可复现、是否可溯源**」：

| 编号 | 目标 | 本阶段验证方式 |
| --- | --- | --- |
| G1 | 登录后可稳定采集 | ⏳ 待真实门户（当前用假门户验证代码路径） |
| G2 | 七项核心字段结构化输出 | ✅ 合成样本上文字型 7/7、图片型 1/7 + 人工清单 |
| G3 | 规则优先 + LLM 兜底的占比可统计 | ✅ 计数与统计口径已验证（LLM 未实跑，见局限） |
| G4 | 每条记录可溯源 | ✅ 每条命中都带原文证据，归档 + 清单可回放 |
| G5 | 人工抽检闭环 | ✅ 固定种子抽样、待人工清单产出 |

**统一口径**（全项目一致，详见 `docs/architecture.md`）：

* 缺失值只有一个写法：**「未知」**；
* 一条记录如果存在「未知」字段，或来自图片 OCR，则**必须**进待人工清单；
* 每个字段的命中都必须带 `evidence`（原文片段），否则不采信。

## 四、实验一：一级规则抽取（离线，不联网）

样本经「清洗 → 分段 → 正则 + 词表」抽取，结果如下：

| 样本 | 命中字段 | 命中数 | 未命中 | 抽取方式 |
| --- | --- | --- | --- | --- |
| `article_text.html` | 七项全中 | **7 / 7** | — | `rule` |
| `article_image.html` | 仅 `graduation_year`（来自标题） | **1 / 7** | grade, degree, major, city, employer, position | `rule` |

**文字型样本的实际抽取结果与证据**（原样摘自运行输出）：

```
graduation_year  2025            ← 我是计算机学院软件工程专业的2025届本科毕业生，大四上学期开始准备秋招
grade            大四            ← 专业的2025届本科毕业生，大四上学期开始准备秋招。本科期间
degree           本科            ← 学院软件工程专业的2025届本科毕业生，大四上学期开始准备秋招
major            软件工程         ← 张三的求职分享我是计算机学院软件工程专业的2025届本科毕业生
city             北京            ← 招一共投了三十多家，最后签约北京的某某科技有限公司，担任算法
employer         某某科技有限公司   ← 秋招一共投了三十多家，最后签约北京的某某科技有限公司，担任
position         算法工程师        ← 签约北京的某某科技有限公司，担任算法工程师，主要做推荐系统的
```

两条值得记录的观察：

1. **单位名做了前缀剥离**：原文是「签约北京的某某科技有限公司」，抽取结果是「某某科技有限公司」——
   靠「城市前缀 + 连接词」剥离规则实现（`rules._strip_location`），否则会把「北京的」带进单位名。
2. **图片型样本不编造**：正文里确实没有任何字段信息，抽取器只从标题拿到届别，
   其余 6 项如实记为「未知」并进待人工清单——这正是 OCR 环节存在的意义
   （见 `docs/storage-decision.md` 的时间账）。

## 六、实验三：OCR 缓存的收益（模型推算 + 已有实测）

本节结论修订自 `docs/storage-decision.md`，数据来源分为**实测**与**估算**两部分，已分别标注。

| 环节 | 数值 | 来源 |
| --- | --- | --- |
| 读 HTML + 解析 300 篇 | 222 ms | 实测（32 线程 SSD） |
| 读 OCR 缓存 600 份 | 21 ms | 实测 |
| 读图片 + sha1 600 张 | 227 ms | 实测 |
| SQLite 全量读 300 行 | 1.3 ms | 实测 |
| OCR 单张耗时 | 1~3 秒 | **估算**（未装 tesseract，需用真实截图实测） |

**关键结论**：命中缓存时一轮 extract 约 **0.24 秒**；未命中缓存则要重跑 OCR，
300 篇（420 张图）约 **7~21 分钟**、10 轮迭代合计 **94~234 分钟**；
加缓存后 10 轮约 **31~45 分钟**。缓存键取**图片内容哈希**，因此同一张图被多篇文章转发时只算一次。

## 九、结论与局限

### 结论

1. **抽取链路成立**：文字型样本七项全中且逐条带原文证据；图片型样本不编造、如实记「未知」并进人工清单。
2. **离线可复现**：extract 阶段完全不联网，规则/词表调整后可反复重跑，60 ms 级完成。
3. **可溯源闭环**：归档 HTML + 内容寻址图片 + 清单 + `evidence` 四件套齐备，页面删除后仍可复核。
4. **工程质量可量化**：204 项测试全绿、覆盖率 82%；实现过程中测试与契约检查共拦下 5 个真实缺陷
   （逐条记录见 `docs/architecture.md` 第十节）。

### 局限（必须与结论分开看）

1. **未接触真实门户**：登录流程、页面选择器、词表白名单尚未按本校门户核对，
   `crawler/session.py` 与 `crawler/login_check.py` 的网络分支未被测试覆盖。
2. **LLM 兜底未实跑**：未配置 API Key，`hybrid` 记录数为 0；只有「降级不中断」的行为被测试覆盖。
3. **OCR 未实跑**：环境未装 tesseract，图片型文章的字段来自人工清单而非 OCR；
   第六节的 OCR 耗时仍是估算值。
4. **样本规模极小**：3 篇样本无法支撑「准确率」这种统计结论，只能证明链路正确。

## 十一、真实门户实验（2026-09-19 首次实跑）

数据来自本校信息门户「就业信息」栏目（`type=10`），**这是本项目第一次接触真实数据**。

### 11.1 采集结果（真实）

| 项 | 结果 |
| --- | --- |
| 分页 | `page_end=2`，每页 15 条 → **30 条通知全部抓到**（翻页验证：两页无重叠） |
| 详情归档 | 30 篇，全部 HTTP 200 |
| 图片归档 | 51 张（按内容哈希命名） |
| 正文来源 | 门户内 21 条 / **站外 9 条**（微信公众号 8 + 腾讯文档 1） |
| 耗时 | 约 8 分钟（30 篇 × 平均 16 秒：浏览器渲染 + ≥2 秒限速 + 图片下载） |
| 解析耗时 | **约 2 秒**（离线，读归档；规则调整后可反复重跑） |
| 导出 | `jobs.csv`（30 行 × 18 列）、`jobs.xlsx`、`manual_review.csv`、`summary.json` |

### 11.2 抽取结果（真实，如实记录）

| 字段 | 命中数 | 完整率 |
| --- | ---: | ---: |
| 学历 | 10/30 | 33.3% |
| 城市 | 11/30 | 36.7% |
| 届别 | 6/30 | 20.0% |
| 年级 | 5/30 | 16.7% |
| 专业 | 2/30 | 6.7% |
| 单位 | 1/30 | 3.3% |
| 岗位 | 1/30 | 3.3% |
| **七项齐备** | **0/30** | 0% |

**结论：本栏目语料与「就业分享文章」的字段口径不匹配。** `type=10` 的“就业信息”实际是
**活动通知/公告**（讲座预告、招聘会安排、选调公告），本身不含“某届毕业生去了哪家单位”的信息。
逐篇线索统计：含「届别」的只有 3/30、含「签约/入职」的仅 **1/30**。

**真正的目标语料在站外的“职点迷津”校友分享系列（微信公众号）**——例如
《“职”点迷津，筑梦起航（第十八期）李香兰学姐的职场进阶之路》，
该篇在规则按真实语料校准后，**七项中抽到 5 项**：

```
届别=2001   学历=本科   城市=北京   单位=北京满分进出口贸易有限公司   岗位=总经理
（依据：「…2001级中国少数民族语言文学专业优秀校友、现任北京满分进出口贸易有限公司总经理李香兰学姐…」）
```

### 11.3 实跑中发现并修复的问题（都有回归测试）

| # | 问题 | 现象 | 修法 |
| - | ---- | ---- | ---- |
| 1 | 列表数组层级 | 取 `tables` 取不到，实际在 `datas.tables` | 列表定位改为「配置 → 常见命名 → **递归下钻**」，并打印实际路径 |
| 2 | **参数提交方式** | 参数放 JSON 体里被服务端**完全忽略**：翻页恒为第 1 页、`pageSize` 恒为 10、`type` 过滤失效（total 44944 而非 1040） | 参数改走**查询串**（实测回显 `currentPage=2, pageSize=15, total=1040`），新增 `api_param_style` |
| 3 | SPA 渲染时序 | 门户 `#/print` 详情页在 DOMContentLoaded 时还是空壳（67 字“加载通知公告数据中…”） | 取 HTML 前等待正文渲染（`_wait_for_render`，阈值 200 字/20 秒） |
| 4 | 微信正文提取 | 站外微信文章退回整页，噪声进正文 | 清洗器新增 `#js_content` / 微信标题选择器 |
| 5 | **假命中：城市** | 「北京大学」被抽成城市「北京」 | 城市改位置感知匹配：后接「大学/学院/公司…」时不算城市 |
| 6 | **假命中：岗位** | 「教师资格培训」→ 岗位=教师；「前公务员考官」→ 岗位=公务员 | 取消「无线索词的岗位兜底」，只认带线索词（担任/现任…）的表述 |
| 7 | **词表未生效** | `aliases.yaml` 的 `employer_cues`/`position_keywords` 其实是硬编码的，改了没用 | 线索词与关键词改为**词表 ∪ 内置**（词表做增量，不删内置能力） |
| 8 | 公司名被吞进岗位 | 「现任北京满分…公司总经理」→ 岗位=「公司名+总经理」 | 岗位正则把公司名做成非捕获的可选前缀 |
| 9 | 城市前缀误剥离 | 「北京满分进出口贸易有限公司」被剥成「满分…」 | 只在城市后跟「的/一/某/该/这/那」时才剥离 |

### 11.4 与合成样本的对比

| | 合成样本 | 真实数据 |
| --- | --- | --- |
| 七项完整率 | 2/3（文字型样本 7/7） | **0/30** |
| 原因 | 样本按七项字段精心构造 | 语料是活动通知，多数字段本就不存在 |
| 价值 | 验证链路与契约 | **暴露了 9 个真实问题**（见 11.3） |

> 合成样本能验证“链路是否通”，但**只有真实数据能验证“规则是否对”**——
> 11.3 里的问题 5–9 全部是合成样本测不出来的。

### 11.5 后续建议

1. **换语料口径**：若要“就业分享文章”，应改用站外校友分享系列（`searchValue` 搜「职点迷津」等关键词），
   或与老师确认本栏目是否是预期数据源；
2. **启用 LLM 兜底**：专业（如“中国少数民族语言文学”）等长尾字段靠词表覆盖不了，正适合 LLM；
