# 存储与缓存方案分析（storage-decision.md）

> 决策问题：**网页数据大部分是图片，是否需要先建数据库？还是直接读 HTML 文件就够快？**
> 本文用实测数据回答，并给出推荐方案与它带来的接口变更。

---

## 一、结论先说

1. **"先建数据库"不是这件事的关键。** 实测：300 篇归档 HTML 全部读+解析只要 **0.22 秒**，
   1000 篇约 0.75 秒。文件直读已经快到无需优化，**为了"读得快"而建库没有收益**。
2. **真正的瓶颈是 OCR。** 图片型文章必须先识别成文字才能抽字段，
   而 OCR 单张要秒级、且**每次重跑都要重算**。实测显示：读 HTML + 解析 + 入库一轮不到 1 秒，
   而重跑 OCR 一轮是**十几分钟**量级——两者差三到四个数量级。
3. **所以要"先行建立"的不是数据库，而是 OCR 结果的持久化缓存**（内容寻址，按图片哈希命名）。
   一轮 extract 从"十几分钟"降到"约 1 秒"，10 轮规则迭代的总耗时从 **2~4 小时降到约 0.5 小时**。
4. **数据库仍然需要，但用途不同**：它不存 HTML / 图片（那属于文件系统），
   只存**结构化结果与状态**——去重、增量入库、导出统计。这部分**现有设计已经具备**
   （`data/employment.db` + `storage/` 层 + `RecordRepository` 接口），无需新建。

一句话：**归档和缓存用文件，结果和状态用 SQLite。** 两者各司其职，不是二选一。

---

## 二、先纠正一个前提

> "现有的系统不依赖数据库"

实际情况是：现有设计**已经有数据库**，只是它不在解析链路上：

| 组成部分 | 现在放在哪 | 是否用 DB |
| --- | --- | --- |
| 原始页面归档（HTML） | `data/raw/html/` 文件 | ❌ 不用（故意的） |
| 采集清单（URL ↔ 文件） | `data/raw/manifest.jsonl` 文件 | ❌ 不用 |
| **中间结果缓存（OCR / 清洗文本）** | —— **当前缺失** | —— |
| 结构化结果 + 复核状态 | `data/employment.db`（SQLite） | ✅ 用 |
| 导出报表 | `data/processed/*.csv/*.xlsx` | ❌ 不用 |

所以现状不是"不依赖数据库"，而是**"数据库只用在最后一环，中间没有缓存层"**。
图片型数据把这个缺口的代价放大了：正文不在 HTML 里，而在图片里，而解析图片是要花秒级算力的。

## 三、实测数据（可复现）

**环境**：WSL2 / Ubuntu，AMD Ryzen 9 8945HX（32 线程），ext4（`/dev/sdd`），SSD。
**样本**：300 篇 HTML（约 40KB/篇，合计 15.5MB）+ 600 张图片（300KB/张，合计 175.8MB），
脚本：`scripts/bench_storage.py`（`python3 scripts/bench_storage.py`，可改 `--articles/--images`）。

| 操作 | 最好(ms) | 中位(ms) | 规模 |
| --- | ---: | ---: | --- |
| A 纯读 HTML 文件 | 29.1 | 30.8 | 300 篇 |
| B 读 + BeautifulSoup(lxml) 解析 | 222.5 | 227.8 | 300 篇 |
| C 读 + BeautifulSoup(html.parser) 解析 | 207.2 | 221.4 | 300 篇 |
| D 读图片字节（不解析） | 38.6 | 40.9 | 600 张 |
| E 读图片 + sha1 哈希 | 227.3 | 228.5 | 600 张 |
| F 读 OCR 缓存文本 | 21.5 | 21.7 | 600 个 |
| G 读 manifest.jsonl | 0.7 | 0.7 | 300 行 |
| H SQLite 批量写 300 行 | 13.9 | 14.0 | 300 行 |
| I SQLite 全量读 300 行 | 1.3 | 1.4 | 300 行 |

**换算成单条成本**（便于外推到任意规模）：

| 单条操作 | 成本 |
| --- | ---: |
| 读 + 解析一篇 HTML | **0.74 ms** |
| 读 + 哈希一张图片 | **0.38 ms** |
| 读一份 OCR 缓存 | **0.036 ms** |
| 写一行 SQLite | **0.046 ms** |
| 读一行 SQLite | **0.004 ms** |

**规模外推（文件路径部分，全部命中缓存）**：

| 规模 | 读+解析 HTML | 读+哈希图片 | 读 OCR 缓存 | SQLite 读 | 合计 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 300 篇 / 600 图 | 0.22 s | 0.23 s | 0.02 s | 0.001 s | **约 0.5 s** |
| 1000 篇 / 2000 图 | 0.74 s | 0.76 s | 0.07 s | 0.004 s | **约 1.6 s** |

**结论**：读写这一层**完全不是瓶颈**。选文件还是选数据库，对速度的影响在这个量级上
可以忽略；真正决定项目能不能快速迭代的是 OCR 与合规限速。

## 四、真正的瓶颈在哪（时间账）

图片型文章的三个时间大头，按量级排列：

| 环节 | 单次成本 | 说明 | 能否优化 |
| --- | --- | --- | --- |
| **① 采集（联网）** | **每请求 ≥ 2 秒**（合规红线，不可调低） | 300 篇 ≈ 300 详情页 + 420 图 = 725 请求 ≈ **24 分钟** | ❌ 不能（红线），只能一次做好、靠缓存避免重跑 |
| **② OCR 识别** | **1~3 秒/张**（估算，见下方标注） | 420 张 ≈ **7~21 分钟** | ⚠️ 算法上难优化，但**结果可缓存** → 第二轮起 0.02 秒 |
| ③ 解析 + 抽字段 | 0.74 ms/篇 + 正则 | 300 篇 ≈ 0.2~1 秒 | ✅ 已经够快 |
| ④ 入库 + 导出 | 0.046 ms/行 | 300 行 ≈ 0.02 秒 | ✅ 已忽略不计 |
| ⑤ LLM 兜底 | 2~5 秒/次调用 | 只有未命中字段才调用 | ⚠️ 可缓存 + 只在必要时调用 |

> **标注（诚实说明）**：②与⑤是**估算**，不是实测——本机没装 tesseract，也没有真实图片样本，
> 所以采用公开经验值：tesseract chi_sim 在 CPU 上处理一页 300 DPI 文档约 1~3 秒。
> 拿到 5 张真实截图后应立即实测（见第七节），实测值可能比估算好或差 2 倍以上。

## 五、两种方案的实际耗时对比

**共同前提**（同一份数据、同样的迭代方式）：

* 规模 A：300 篇文章，70% 为图片型（= 210 篇）、每篇 2 张图 → **420 张待 OCR**
* 规模 B：1000 篇文章，同样比例 → **1400 张待 OCR**
* 迭代方式：调整正则/词表后重跑 `--stage extract`，共 **10 轮**（这是规则调优的常见轮次）
* 采集只做一次（合规限速决定，无法压缩）

| | 方案一：纯文件，不缓存 OCR | 方案二：文件归档 + **OCR 缓存** + 结果入 SQLite（推荐） |
| --- | --- | --- |
| 首轮采集 | 24 分钟（300 篇） | 24 分钟（相同，红线决定） |
| 首轮 OCR | 7~21 分钟 | 7~21 分钟（相同，必须算一次） |
| 每轮 extract | **重新 OCR：7~21 分钟** | **读缓存 + 解析 + 入库：约 1 秒** |
| **10 轮总耗时（300 篇）** | 24 + 10×(7~21) ≈ **94~234 分钟** | 24 + (7~21) + 10×1s ≈ **31~45 分钟** |
| **10 轮总耗时（1000 篇）** | 80 + 10×(23~70) ≈ **310~780 分钟（5~13 小时）** | 80 + (23~70) ≈ **103~150 分钟（1.7~2.5 小时）** |
| 去重与幂等 | 靠脚本自己扫目录比对，易错 | SQLite 唯一约束 + 哈希缓存键，天然幂等 |
| 断点续跑 | 需自己记录"哪些做过了" | 缓存命中即跳过，天然支持 |
| 数据可读性 | ✅ 能直接 grep / 打开看 / tar 备份 | ✅ 归档仍是文件，DB 只存结果 |
| 依赖 | 无 | 无（sqlite3 是标准库） |
| 结论 | ❌ 迭代成本高，且随轮次线性恶化 | ✅ **推荐** |

**差异来源只有一处**：OCR 结果有没有存下来。
也就是说，**要不要"先建库"其实是个伪命题；要不要"先做缓存"才是真问题。**

### 为什么不用数据库存 HTML / 图片

| 理由 | 数据支撑 |
| --- | --- |
| 体量级差太大 | 300 条结果仅 **104 KB**；而 HTML 归档 15.5MB、图片归档 **175.8MB**（相差约 1700 倍） |
| 读文件本来就快 | 读+解析 300 篇 0.22 s，放进 DB 也只是把文件 IO 换成 blob IO，不会更快 |
| 文件更好用 | 可以直接 grep 全文、用浏览器打开复核、用 tar/rsync 增量备份、崩了也不会损坏 |
| DB 会变脆 | blob 进库后，备份/迁移/损坏恢复成本都上升，而收益为零 |

**DB 真正的价值在"语义"而不在"速度"**：唯一约束去重、事务、聚合统计、复核状态回写、断点状态。
这些正是 `jobs` 结果表要解决的事——**现有设计已经覆盖，不需要新建**。

## 六、图片型数据暴露的接口缺口（需要补）

现有契约假设"正文在 HTML 里"。图片型文章会直接击穿这个假设：

```
RawArticle.html 无正文  →  CleanArticle.body 为空  →  七项字段全部「未知」  →  全部进待人工清单
```

也就是说：**不改接口，采集能跑通，但抽取结果会大面积为空**。建议的契约变更（`SCHEMA_VERSION` 1.0.0 → 1.1.0）：

| # | 变更 | 目的 |
| - | ---- | ---- |
| 1 | 新增 DTO `ImageAsset`（`image_path` / `sha1` / `source_url` / `ocr_cache_path` / `ocr_status`） | 让"图片"成为一等公民，可追踪 |
| 2 | `ManifestEntry` 增加 `images: List[ImageAsset]` | 离线回放时知道这篇文章有几张图、都在哪 |
| 3 | `CleanArticle` 增加 `source_kind: "html" \| "ocr" \| "mixed"` | 区分文本从哪来，统计与抽检都需要 |
| 4 | 新增路径规则函数 `ocr_cache_relpath(image_sha1, cache_dir)` | 与 `raw_html_relpath` 同构，保证缓存键确定、可重建 |
| 5 | `COUNTER_KEYS` 增加 `images_fetched` / `ocr_cached` / `ocr_computed` / `ocr_failed` | 让"OCR 省了多少时间"变成可量化指标 |
| 6 | 校验口径：`source_kind == "ocr"` 的记录 `review_status` 强制 `pending` | 落实合规红线 5「OCR 结果一律人工复核」 |

注意第 4 条是**最关键的一条**：缓存键必须是**图片内容的哈希**，而不是文件名或序号。
理由：同一张图在不同文章里重复出现（转发同一张截图）时，内容哈希能自动命中同一份缓存；
而按文件名或序号做键，换个页面就重算一遍。

**变更流程**（已有约定，不能跳步）：递增 `SCHEMA_VERSION` → 改 `src/contracts.py`
→ 改 `tests/test_contracts.py` → 改 `docs/architecture.md`。

## 七、推荐方案与实施顺序

**推荐：双轨存储 + 内容寻址缓存**

```
data/
├── raw/
│   ├── html/<article_key>.html        # 正文=文字的文章原文（已有）
│   ├── images/<article_key>/          # 正文=图片的文章，图片按文章归档（新增）
│   ├── ocr/<image_sha1>.txt           # ★ OCR 结果缓存：按图片内容哈希命名（新增，关键）
│   └── manifest.jsonl                 # 增加 images 字段（新增）
├── processed/{jobs.csv,jobs.xlsx,manual_review.csv}
└── employment.db                      # 结构化结果 + 复核状态（已有，不动）
```

**实施顺序**（P0 决定迭代速度，先做）：

| 优先级 | 事项 | 产出 | 预计工作量 |
| --- | --- | --- | --- |
| **P0** | 图片归档 + OCR 缓存（内容寻址） | `data/raw/images/`、`data/raw/ocr/<sha1>.txt` | 半天（含 `session`/`detail_page` 改造） |
| **P0** | 契约升级到 1.1.0（第六节 6 条） | `contracts.py` + 契约测试 + 架构文档 | 半天 |
| **P1** | 实测 OCR 单张成本（用 5 张真实截图） | 替换本文第四节估算值 | 1 小时 |
| **P1** | `--stage extract` 走缓存命中路径 | 一轮 extract ≤ 数秒 | 与 P0 合并 |
| **P2** | 结果入库与导出（现有设计，直接实现） | `jobs.csv` / `jobs.xlsx` | 1 天 |
| **P3** | 规模上来后的增强（>5000 篇 / 需全文检索时） | SQLite **FTS5** 索引 OCR 文本；`images` 单独建表 | 需要时再做 |

**不建议做的事**：

* ❌ 把 HTML / 图片读进数据库当 blob（体量差 1700 倍，收益为零）
* ❌ 为了"读得快"而先建库（实测读文件已经 0.22 秒/300 篇）
* ❌ 每次 extract 重新 OCR（这是当前唯一会浪费小时级时间的设计缺口）
* ❌ 提高并发来压缩采集时间（违反"只读低频 ≥2 秒"的红线）

## 八、何时才需要重新考虑（触发条件）

出现下面任一情况，再把 DB 的角色加重（属于渐进增强，不需要推翻现在的设计）：

| 触发条件 | 届时做法 |
| --- | --- |
| 文章数 > 5000，需要按字段做复杂查询/联表 | 结果表加索引；图片、OCR 元数据单独建表 |
| 需要在 OCR 文本里做全文检索/相似文章聚类 | 引入 SQLite **FTS5**（仍是标准库，无新依赖） |
| 需要多进程并发采集/解析 | 用 SQLite 做状态锁（WAL 模式），文件缓存仍是内容寻址 |
| 需要长期多人协作、增量更新 | 把 `manifest.jsonl` 迁入 DB 表（此时它已不适合追加式文件） |
