# 检索层（search.md）

> 本文说明「类百度检索页面 + 三级缓存 + 有倾向性采集」这一层怎么工作、为什么这样设计，
> 以及它的**能力边界**。设计动机与踩坑记录一并写在正文里——因为这些坑的共同特征
> 是"不报错、只是静默返回空结果"，不写下来下次还会踩。

对应实现：`src/search/`（7 个文件），新增 42 项回归测试（`tests/test_search.py`）。
契约版本：`SCHEMA_VERSION = 1.5.0`。

---

## 一、它解决什么问题

原项目的输出是**离线文件**（`jobs.csv` / `jobs.xlsx` / `report.html`），
要看结果得先跑脚本再打开文件。检索层把同一份结构化结果变成**可交互的检索服务**：

```
用户输入关键词
   ↓
① 规范化查询意图（切词 + 字段过滤 + 分页夹取）
   ↓
② L1 进程内 LRU ──命中──→ 返回（微秒）
   ↓ 未命中
③ L2 SQLite 查询缓存 ──命中──→ 返回（毫秒）
   ↓ 未命中
④ L3 FTS5 全文检索 ──→ 结果 + 片段高亮 + 关联词
   ↓
⑤ 命中不足？→ 生成「采集建议」（**只建议，不擅自联网**）
   ↓
用户在页面上确认 → 定向采集（后台作业，受三道闸门约束）
```

## 二、三级缓存：为什么要三级，以及各级的真实价值

| 级 | 位置 | 命中成本 | 失效方式 | 真实价值 |
| - | ---- | -------- | -------- | -------- |
| L1 | 进程内 `LruCache`（默认 128 条） | 微秒 | 随进程结束 | 挡住"同一秒内的重复请求" |
| L2 | 表 `search_query_cache` | 毫秒 | **数据版本号** + TTL | **跨进程存活**（服务重启后仍命中） |
| L3 | `articles` + FTS5 | 毫秒 | —— | 真相来源 |

### 诚实的说明：单进程下 L2 几乎不会被命中

`search()` 的顺序是 L1 → L2 → L3，而 L3 命中后会**同时回填 L2 与 L1**。
因此同一进程里第二次查同一个词，命中的一定是 L1——L2 被 L1 遮住了。

L2 的价值不在于"同进程更快"，而在于**跨进程**：

* 跑完 `--stages extract` 的 CLI 进程退出后，它的 L1 消失了，但 L2 留在库里；
* Web 服务重启（改代码、换端口）后 L1 清空，L2 还能直接命中。

`tests/test_search.py::test_service_three_level_cache_and_invalidation` 就是按
"新建一个服务实例 = 模拟重启"来断言 L2 命中的，而不是假设同进程能命中 L2。

### 失效为什么用「版本号」而不是「标脏」

缓存键 = `sha256(规范化查询 | 数据版本号)`。任何写入让版本号 +1，旧键**自然不再被查中**：

* 不需要"写完再回头标记哪些缓存行脏了"（既慢又容易漏）；
* 不存在脏读窗口；
* 不需要让每一条写路径都记得清缓存。

代价是旧行会暂时占空间，由 `QueryCache.prune()` 按 TTL + LRU 回收。
版本号存在 `search_meta.index_version`。

### 写路径的钩子：为什么不是存储层自己做

存储层（`src/storage`）**只允许依赖 contracts/config**，不允许反向依赖检索层
（见 `tests/test_contracts.py` 的分层表）。所以"写完重建索引"这件事通过一个
**可注入回调** `after_write` 挂上去：

```python
repo = build_repository(cfg, after_write=service._index.maintain)
```

不传回调时退化为纯存储，行为与历史版本完全一致（导出一致、幂等一致）。

## 三、L3：FTS5 索引

### 表结构与同步方式

```
articles                  ← content 表（真相来源，含派生列 index_text）
  └─ index_text           ← 派生列：标题(加权2次) + 七项字段 + 命中依据，剔除「未知」
articles_fts              ← FTS5 external-content 索引（不复制正文，体积几乎不增）
search_meta               ← index_version
```

**不用触发器**。这是三次踩坑后的结论：

1. 触发器早于 `index_text` 派生列创建 → 触发器体引用不存在的列，
   SQLite 报的不是"列不存在"，而是极具误导性的 `database disk image is malformed`；
2. `AFTER UPDATE` 触发器里的 FTS `'delete'` 命令在"批量刷派生列"时自触发，把倒排索引写坏；
3. 最致命：为递增版本号而在写事务未提交时**另开一条连接**操作同一个 WAL 库，
   两条连接交叉维护 FTS 表 → 索引损坏。

现在只有一条路径：**写完由写方在自己的连接上调用 `maintain()`**
（刷新派生列 → FTS `'rebuild'` → 版本号 +1）。`init_schema()` 还会顺手清掉历史触发器。

### 必须剔除占位符「未知」

七项字段缺失时一律填「未知」。若不剔除，真实库 30 条**几乎条条含它**，
任何查询都会命中全表，相关性排序彻底失效。`row_to_index_text` 与
`_build_index_text_sql` 是同一口径的两条实现（Python / SQL），
测试用 `test_index_text_excludes_missing_placeholder` 钉住。

### 分词器：默认 `unicode61`，这是实测结论

| 分词器 | 2 字中文（硕士/北京/本科） | 子串（招聘 → 招聘会） | 结论 |
| ------ | -------------------------- | --------------------- | ---- |
| `trigram` | ❌ 实测 `MATCH '"硕士"'` = **0 行** | ✅ | 最常用的中文查询词全部失效 |
| `unicode61`（默认） | ✅ 能命中且给 bm25 分 | ❌ 整段中文是一个 token | 作为主路径 |

所以本层采用**双路径**：

* **主路径**：`unicode61` + FTS5 `MATCH`（`"北京" AND "硕士"`），带 bm25 相关性排序
  （`bm25()` 返回负值，**越小越相关**，故按 ASC 排序）；
* **兜底路径**：主路径**查不到任何行**时，改用原始查询串做 `LIKE` 子串扫描，
  补上 `招聘 → 招聘会` 这类子串语义。此时 `score` 恒为 0，
  这是**如实反映**（该路径没有相关性排序，不假装有分）。

两条路径的取舍由 `count_matching` 与 `fetch_rows` **同步决策**，
保证 `total` 与实际命中数一致——否则前端分页会承诺不存在的页。

需要纯子串语义时改 `search.fts_tokenizer: trigram`（长词场景），
`init_schema()` 检测到分词器变化会自动重建索引。

## 四、有倾向性采集

### 关键前提：门户自带服务端检索

门户列表接口 `getNoticeByPage` 的参数表里本来就有 **`searchValue`**
（`config/config.yaml` 的 `portal.api_body`）。所以"有倾向性"不是本地过滤出来的，
而是**让服务端只返回相关的**——既省请求（合规红线 ≥2 秒/请求）也省时间。

实现：`fetch_list_api(..., search_value=...)` → 塞进查询串。
未传该参数时行为与全量采集**完全一致**（向后兼容，`PageFetcher` 协议不变）。

另有一道**本地标题兜底过滤**：实测门户关键词检索是宽松匹配，
可能返回标题里并不含查询词的条目，这类"擦边"结果不入库——
否则一次定向采集会变成一次小规模全量灌库。

#### 实测：门户 `searchValue` 的真实语义（重要）

门户把关键词包成 `LIKE '%关键词%'`（响应里 `datas.page.searchValue` 会**回显**实际模式）。
但它的行为有几个不直观之处，**全部是实测结论**：

| 输入 | 返回 | 说明 |
| ---- | ---- | ---- |
| `迷津` | 3 条 | 正常过滤 |
| `点迷津` | 3 条 | 正常过滤 |
| `教师资格` | 10 条 | 正常过滤 |
| `职点迷津` | **0 条** | 语料里写作 `“职”点迷津`，**引号把连续子串切断** |
| `职点` | **0 条** | 同上（跨在引号上） |
| `职` | 15 条 | 单字会退化成"整页未过滤"，白花一次请求 |
| `招聘` / `就业` / `选调` | 15 条 | 语料里常见词，接近未过滤 |

**结论：用户输入的关键词未必能在语料里连续出现**（标点/引号位置无法预知），
所以"挑一个正确关键词"本质上是在猜标点位置。因此实现改为
**枚举候选 + 逐个试，取第一个有结果的**（`portal_candidates_of`）：

1. 按标点切出的整段（标点位置正是语料里可能的断点）；
2. 该段的短后缀（`职点迷津` → `点迷津` → `迷津`），后缀能绕过"词内夹标点"；
3. 去重后按长度降序，长词优先（更精确）；
4. 最多试 `MAX_KEYWORD_CANDIDATES`（4）个候选，把额外请求数钉死。

于是用户搜「职点迷津」时：先用 `职点迷津`（0 条）→ 再试 `点迷津`（3 条）命中。
`pages_fetched` 如实计入这些重试请求，不美化。

**踩坑记录（值得记下来）**：我一开始想把关键词"截短到 3 字"来解决，
得到 `职点迷`——而它**恰好跨在引号上**，那个片段在语料里根本不存在，
0 召回，比不截还糟。教训：**不要猜标点位置，直接枚举候选试**。

#### 先登录，否则必然失败

未登录时门户对接口请求返回 **HTTP 200 + 统一身份认证登录页 HTML**（不是 401），
JSON 解析失败，错误会伪装成"接口返回不是合法 JSON"。
因此定向采集与 `pipeline --stage fetch` 一样有**登录门禁**：

* `run_targeted_fetch` 第一步就调 `require_login(cfg)`；
* `SearchService.request_fetch` 在**起后台线程之前、消耗冷却之前**先过门禁，
  这样用户立刻拿到"请先跑 login_check"的明确提示，
  而不是等一分钟拿到一个后台失败、还把冷却额度浪费掉；
* 顺带修了错误文案：响应是 HTML 时直接判定为登录态失效并给出修复命令。

### 三道闸门（缺一不可）

| 闸门 | 配置项 | 默认 | 作用 |
| ---- | ------ | ---- | ---- |
| 总开关 | `search.trigger_enabled` | **false** | 默认完全离线：只建议、零网络请求 |
| 冷却 | `search.fetch_cooldown_seconds` | 900 | 同一查询串 15 分钟内只允许一次 |
| 预算 | `search.max_estimated_seconds` | 120 | 预估耗时超上限直接拒绝 |

预估耗时**按最坏情况算且不美化**：

```
请求数 = 1（列表页）+ max_fetch_pages(2) × 15（每页详情） = 31
预估秒数 = 31 × request.interval_seconds(2.0) = 62 秒
```

页面上会原样显示这两个数字，让用户在点"采集"之前就知道代价。
`test_request_fetch_estimates_cost_honestly` 钉住这个口径。

### 为什么必须异步

31 次请求 × 2 秒 ≈ 62 秒。同步执行会让 HTTP 请求挂死、前端以为页面崩了。
因此 `POST /api/fetch` 立即返回作业 id，后台线程执行，前端轮询
`GET /api/fetch/<job_id>`。作业状态落表 `search_fetch_jobs`，
所以**刷新页面后进度条能恢复**（`latest_job()`）。

采集完成 → 入库 → 版本号 +1 → L1/L2 自动失效 → 页面自动重查，立刻能看到新数据。

## 五、Web 层

### 为什么用标准库 `http.server`

项目一贯取舍是"不为单职责引入依赖"（sqlite3 而非 ORM、FTS5 而非 Whoosh）。
本服务只做「只读查询 + 一个后台作业」，路由不到 10 条，标准库够用；
引入 Web 框架会让 `requirements.txt` 多出十几个包，却换不来这个规模下的实际收益。
代价是路由与 JSON 手写——`src/search/server.py` 就是那份代价。

### 两条硬性安全约束

1. **只监听回环地址**：`config.validate_config` 强制 `search.host` ∈
   `{127.0.0.1, localhost, ::1}`，填别的直接配置报错。该服务返回真实抓取内容，
   绝不允许对外监听。
2. **不信任查询参数**：`limit` 夹到 `search.max_limit`；`offset` 不得为负；
   字段过滤只接受七项核心字段名（杜绝任意列名进 SQL）；
   静态文件做路径穿越防护（`resolve()` 后校验前缀）。

### 端点

| 方法 | 路径 | 说明 |
| ---- | ---- | ---- |
| GET | `/api/search?q=&limit=&offset=&<字段>=` | 检索（三级缓存） |
| GET | `/api/related?q=` | 关联词建议 |
| POST | `/api/fetch` | 触发定向采集，返回作业 id（202 / 409） |
| GET | `/api/fetch` | 最近一次作业（刷新后恢复进度条） |
| GET | `/api/fetch/<job_id>` | 作业状态 |
| GET | `/api/stats` | 索引版本、命中数、缓存量、采集开关 |
| GET | `/`、`/style.css`、`/app.js` | 前端页面（`src/search/web/`） |

### 前端

原生 HTML/CSS/JS，**零构建、零 CDN**（内网/离线也能打开）：

* 空查询时检索框居中放大（首页观感），有结果后收窄到顶部（结果页观感）；
* 每条结果显示：标题、命中片段（`<em>` 高亮）、七项字段标签、命中依据、
  **字段完整度 n/7**、发布时间、"回原文核对"链接（可溯源）；
* 关联搜索：点击推荐词会**并进**当前查询而不是替换，保留用户原始意图；
* 侧栏显示数据来源徽标（进程内缓存 / 查询缓存 / 库内检索）+ 耗时 + 数据版本号。

**一段安全约定**：结果标题与片段都来自**抓取的第三方网页文本**，
因此前端先 `stripTags` 再按检索词重新包 `<em>`——即"不直接信任后端 HTML"。
后端也已做 `html.escape`，两层都有防护。

## 六、能力边界（务必知道，避免误用）

1. **语料问题没有被这一层解决。** `type=10` 栏目仍是活动通知/公告，
   七项齐备 0/30 的根因是语料口径不匹配（见 `experiment.md` 第十一节），
   检索层只是让既有结果**可查**。真正的目标语料仍是站外的「职点迷津」分享系列。
2. **`unicode61` 下同义词不互通**：搜「计算机」匹配不到「软件工程」。
   本层的"关联搜索"推荐的是**库内真实出现过的字段值**（按频次），
   不是语义相似词——这样推荐了必有结果，但不会做语义扩展。
3. **`LIKE` 兜底路径无相关性排序**（`score` 恒 0），且是全表扫描。
   当前 30 条/1040 条量级完全可接受；上万条时应改 `trigram` + 应用层切词。
4. **单页上限 `search.max_limit`（默认 100）**：默认是"防前端构造
   `limit=999999` 把整库拖进内存"，不是性能优化。
5. **`related` 与 `suggestion` 是两件事**：前者是搜索结果的补充维度（库内真实词），
   后者是"库内不够用，要不要去门户采集"的建议。
6. **缓存里没有正文**：`snippet` 由标题/字段/命中依据拼成。
   项目未把正文入库（`docs/storage-decision.md` 的取舍），因此片段信息量有限。

## 七、可观测与运维

`GET /api/stats` 返回：

```json
{
  "index_version": 4,
  "indexed_rows": 30,
  "query_cache_rows": 2,
  "l1_entries": 2,
  "l1_hits": 0,
  "l1_misses": 2,
  "trigger_enabled": false,
  "db_path": ".../data/employment.db"
}
```

排查思路：

| 现象 | 先查 |
| ---- | ---- |
| 搜不到明明存在的内容 | `indexed_rows` 是否为 0？索引是否落后于 `articles`？（`rebuild`） |
| 搜 2 字词没结果 | `search.fts_tokenizer` 是否被改成了 `trigram`？ |
| 改了代码结果不变 | Quarto 级别：L2 缓存。数据版本号只随**数据**变，不随**代码**变 |
| 采集按钮不可点 | `trigger_enabled` 关了？还是冷却中（`blocked_reason` 会写明） |
| 采集完结果没变 | 看作业状态与 `records_inserted`；0 条说明门户检索没召回 |

> 注意：**改匹配逻辑不会让缓存失效**（版本号只跟数据走）。
> 开发期请顺手清一次 `search_query_cache`，否则会看到旧口径的结果。
